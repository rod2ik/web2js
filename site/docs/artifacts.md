# Runtime artifacts

The runtime contract between Web2js and TikZJax is represented by exactly four files in `dist/`.

```text
dist/
├── tex.wasm
├── tex.wasm.gz
├── core.dump
└── core.dump.gz
```

## `tex.wasm`

`tex.wasm` is the optimized and Asyncify-enabled WebAssembly module generated from the TeX WEB sources through the Web2js Pascal compiler.

It contains the executable TeX engine logic. On its own, it does not contain the initialized LaTeX/TikZ state.

## `core.dump`

`core.dump` is a byte-for-byte dump of the initialized WebAssembly memory after `initex` has prepared the LaTeX/TikZ runtime.

TikZJax therefore needs the logical pair:

```text
tex.wasm + core.dump
```

The first supplies executable WebAssembly code; the second supplies the initialized memory state expected by that code.

A changed `core.dump` can therefore change the preloaded LaTeX format even when the JavaScript side of TikZJax has not changed.

## Compressed runtime: `tex.wasm.gz` and `core.dump.gz`

The `.gz` files are generated by `scripts/build/gzip-artifacts.mjs` as part of `yarn build`.

They are the deployment-friendly/browser-facing representation used by the TikZJax runtime workflow, while the uncompressed files remain the canonical raw artifacts used for integrity checks and release distribution.

Compression belongs to Web2js rather than TikZJax so that the artifact handed to TikZJax is already final:

```text
Web2js build
   │
   ├── tex.wasm ───────► tex.wasm.gz
   └── core.dump ──────► core.dump.gz
                         │
                         ▼
                 yarn deploy:tikzjax
```

TikZJax should not silently rebuild or recompress these files during the handoff.

## Integrity invariant

The required invariant is:

```text
gunzip(tex.wasm.gz)  == tex.wasm
gunzip(core.dump.gz) == core.dump
```

Run:

```bash
yarn validate:dist
```

The validator confirms:

1. all four files exist;
2. all four files are non-empty;
3. `tex.wasm.gz` expands exactly to `tex.wasm`;
4. `core.dump.gz` expands exactly to `core.dump`.

## Versioning and releases

The four files in `dist/` are release deliverables. Three are small enough to be tracked directly by Git; `dist/core.dump` is intentionally ignored because its uncompressed size exceeds GitHub's regular 100 MiB Git object limit. `dist/core.dump.gz` is tracked, and the release workflow reconstructs `core.dump` from it before validation and before creating the project ZIP. A GitHub Release created from `vX.Y.Z` still attaches all four runtime artifacts.

This makes it possible to identify exactly which runtime was published by a Web2js version and then consumed by a TikZJax development/release cycle.
